# DSH 插件使用率与能力分析系统 · 需求文档（PRD）

> 版本：v0.3（归属解析层优先）
> 适用：DeepSeek Harness（dsh）插件生态
> 目标：回答「哪个插件真在被用、被怎么用、它到底提供什么能力」
>
> **本文是 PRD，不是 ADR**：它记录需求与原则，不记录已作出的架构决定。相关架构
> 决定见 [`0003-插件归属解析.md`](./0003-插件归属解析.md)；§6「待确认」里的归属
> 来源、对外暴露与保留期已在 ADR-0003 中落定。

---

## 1. 背景与问题

现有 dsh 统计类插件集中在：

- Token / 费用 / 会话时长（usage-stats 系列）
- 工具调用次数（tool-call-stats、plugin-usage-analytics）
- Skill 使用次数（dsh-skill-stats）

共性缺陷：

1. **无稳定「调用 → 插件」归属**：靠 tool 名反查，fork / hook 注入会丢归属
2. **显式与隐式入口混算**：按钮点击 ≠ 模型自动选工具，放同一分母失真
3. **无插件能力档案**：不知道插件「能做什么」，只统计「调了几次」
4. **底层接口变动脆弱**：事件名一改，统计逻辑全崩

---

## 2. 设计原则

- 先建「归属解析层」与「能力档案」，再做统计与推荐
- 本地优先，不出站；不做远程 SaaS
- 口径分层：显式 / 隐式 / 加载存活，不强行合并
- 归属解析与业务统计解耦，底层适配可插拔

---

## 3. 核心模块

### FR-1 采集层（薄）

只负责订阅 dsh 运行时事件，不做归因：

- `tools/pre-execute` / `tools/result`
- `command/run`
- `skill/invoke`（或 skill tool 调用）
- `agent/session-start` / `agent/pre-step`
- 插件 manifest 加载完成事件

输出：原始事件流 → 交给归属层。

---

### FR-2 归属解析层（Attribution Resolver）【P0 优先】

职责唯一：**「给定一次调用，回答这是哪个插件的」**。

#### 输入

- 运行时事件（tool 名、command 名、skill 名、hook 点）
- 静态注册信息（插件 manifest：id、导出 tools / commands / skills / hooks）

#### 输出

- `resolve(event) → { pluginId | "builtin" | "unknown", confidence }`
- `getAttributionMap() → Map<callableName, pluginId>`
- `listPlugins() → PluginMeta[]`

#### 双源关联策略

1. 静态注册表：扫描已安装插件 manifest，建立 名称→插件 初始表
2. 运行时观察：事件触发时反查，命中则加固；未命中标 unknown
3. 版本适配器：
   - adapter-v1 / v2 / latest
   - dsh 改事件协议只改适配器，上层无感
4. 未来若 dsh 提供官方映射：加 `adapter-official` 无缝切换

#### 质量要求

- 不硬猜：无法确认归属如实标 unknown，不污染统计
- 可缓存：manifest 不变不重复解析

---

### FR-3 插件能力档案（Capability Profile）【P0 与 FR-2 并列】

每个插件在注册 / 加载时生成一份能力档案，用于构建「能力分析矩阵」。

#### 能力维度（预分类，可扩展）

| 维度 | 二级枚举（示例） |
|---|---|
| UI 扩展 | 节点渲染 / 侧边栏面板 / 设置页 / 命令面板 / 无界面 |
| 模型交互 | 系统提示注入 / 上下文注入 / 模型调用封装 / 无 |
| 工具提供 | 原生 tool / MCP tool / 复合 tool / 无 |
| Skill 提供 | 指令型 / 工作流型 / 无 |
| Hook 点 | 会话级 / 步骤级 / 工具级 / 输出级 / 无 |
| 数据 / 存储 | 本地 JSON / DSH_HOME / 外部 API / DB / 无 |
| 权限 / 安全 | 只读 / 网络 / 文件系统 / 凭证 / 高危操作 |

#### 档案字段

```
{
  pluginId, name, version,
  capabilities: { ui:[], model:[], tools:[], skills:[], hooks:[], data:[], auth:[] },
  declaredButInactive: bool,   // 声明了 tool 但从未被调用
  firstSeen, lastLoaded
}
```

#### 用途

- 能力重叠检测（多个插件做同一件事）
- 插件推荐（「你常用 X 工具，缺 Y 能力」）
- 冲突预警（同 hook 点多插件拦截）
- 统计语义增强（知道「谁」和「能做什么」）

---

### FR-4 使用率统计层（基于 FR-2 / FR-3）【P1】

#### 三类口径（不合并排行）

1. **显式使用率**
   - 分子：command/run、用户主动 tool 调用
   - 分母：active_sessions
2. **隐式命中率**
   - 分子：模型自动选 tool / skill 命中 / hook 触发
   - 分母：agent_steps
3. **加载存活率**（纯 UI / 常驻插件）
   - 分子：被加载且渲染过
   - 分母：dsh 启动次数

#### 指标

- 调用次数、错误率、P95 耗时
- 跨会话数、近 30 天活跃
- 「安装未激活」标记

---

### FR-5 分析面板与导出【P2】

- 侧边栏面板：插件排行（分显式 / 隐式）
- 能力矩阵视图：行 = 插件，列 = 能力维度
- 本地导出 JSON / CSV（无凭证、无对话正文）

## 6. 待确认

1. manifest 能否稳定拿到「导出 tool / command / skill」列表？
   → **不能**。查证结论：`ToolDefinition` 无 owner 字段、`ctx.tools.register()` 不
   记录调用方、`DshManifest` 不声明导出的工具。改走「插件自报 + 前缀启发式」两级
   来源，见 [ADR-0003](./0003-插件归属解析.md)。
2. 能力分类是否允许用户自定义标签？
   → 留到 FR-3（能力档案）再定，本次不做。
3. 归属层是否对其它插件暴露内部 API？
   → **暴露，但只读**：`ctx.provide('pluginInsight')` 提供 `resolve` /
   `listPlugins` / `getAttributionMap` / `eventsFile` 四个只读方法，属内部 API，
   不承诺跨版本稳定。
4. unknown 归属数据保留多久？
   → 原始事件行 **30 天滚动**，计数聚合永久保留。
