# ADR-0003: 插件归属靠「自报声明 + 前缀启发式」两级来源，不等上游官方映射

**Date:** 2026-11-10
**Status:** Accepted
**Author(s):** dsh-toomuch-plugins maintainers
**Deciders:** 插件维护者

---

## Context

`docs/adr/0002-dsh插件使用率与能力分析系统需求.md`（PRD，v0.3）要求实现 FR-1
采集层与 FR-2 归属解析层。落地前查证了 DSH 运行时，结论与 PRD 的假设有出入：

1. **PRD 待确认 #1 的答案是「不能」。** 运行时没有任何 API 能把 tool / command /
   skill 名映射到所属插件：
   - `ToolDefinition`（`dsh-tools/lib/types/contracts.d.ts:23`）没有 owner /
     plugin 字段；
   - `ctx.tools.register()`（`dsh-tools/lib/index.js:433-445`）把工具插进
     **全局 layer**，不记录调用方——loader 的每个 bundle 行都注册进同一层，
     没有 owner 痕迹；
   - 插件 manifest（`DshManifest`，`dsh-package-manifest/lib/types/types.d.ts:30-39`）
     只有 `bundle` / `profile` / `client` 三段，不声明导出的工具。
   ⇒ FR-2 原文写的「扫描已安装插件 manifest，建立 名称→插件 初始表」**写不出来**。

2. **FR-1 原文的事件表一半不存在。** 真实存在的是 `tools/pre-execute`
   （waterfall）、`tools/result`（emit）、`agent/pre-step`、`agent/created`、
   `session/event`、`plugin-manager/changed`；而 `skill/invoke` 与
   `agent/session-start` **不存在**，`command/run` 只是会话日志里的事件类型
   （`dsh-commands/lib/types/types.d.ts:101`），不是 cordis 事件。

3. **运行时没有「显式 vs 隐式」字段。** `ToolExecution`
   （`contracts.d.ts:163-213`）没有 `source` / `trigger` / `explicit` 之类字段，
   全树 grep 无此类字段；`tool/call` 事件**只由模型驱动管线产出**
   （`dsh-tools/lib/types/batch.js:210`）。用户主动的入口是斜杠命令
   （`command/run` 带 `source.kind='user'`）与手写 `/技能名` 手势。

4. **可归属的模块清单拿得到**：`ctx.loader.entries()` 给出每个 bundle 行的
   `options.id` 与 `options.name`（模块说明符），零新增依赖。

5. **命名约定确实存在**，但不是简单等值：本机 profile 的 36 个 bundle 行与实际
   工具名的对照显示——`docker_exec` ↔ 行 id `docker`（精确）、`skill_manager_list`
   ↔ 行 id `skill-manager`（下划线↔连字符归一化后精确）、`deck_context` ↔
   `dsh-mattpocock-skills-deck`（落在模块名的一段）、`study_workspace` ↔
   `study-suite-runtime`（同上，且该模块占 7 行，需按模块去重）。

6. **落点冲突**：本仓库的公开身份是侧栏 UI 插件（marketplace `category: ui`，
   client 半边是浏览器 React），而 FR-1 需要**常驻宿主侧采集器**。仓库自己的
   `docs/design.md:301` 已有先例——「那更适合 `dsh-sidebar-quiet` 这类插件去做」。

**Key constraints:**

- 本仓库已声明的边界（`docs/design.md` §2）：不注入 DSH 内部模块、不读写 DSH
  配置、偏好只写 `localStorage`、唯一落盘是自己 Host 半边的私有文件。
- 本地优先、不出站；口径分层（显式 / 隐式 / 加载存活）不合并。
- 不硬猜：认不出来的归属如实标 unknown，不污染统计。

---

## Options Considered

### Option 1: 等上游 DSH 提供官方的「工具名 → 插件」映射

**Description:** 不自建归属规则，等 DSH 在 `ToolDefinition` 或 manifest 里补上
owner 信息，再照着官方契约实现。

**Pros:** 唯一能拿到**精确**归属的路径；没有命名约定的脆弱性；不必维护任何
启发式。

**Cons:** 时间不可控；上游未必会加（这属于 DSH 内部实现细节，不是公共契约）；
期间整个系统无法落地。

**Why this was ruled out (if not chosen):** 不可控的等待不是方案。归属层要能在
**今天**工作，同时为官方映射留一个可替换的位置。

---

### Option 2: 只做插件自报声明（package.json 的 `dsh.capabilities`）

**Description:** 插件在自己的 manifest 里精确列出导出的 tool / command / skill，
归属层只认自报，认不出就 unknown。

**Pros:** 精确、无歧义；声明本身就是一份可读的「插件能力档案」，FR-3 能直接用；
声明式契约比运行时推断更容易跨版本存活。

**Cons:** **今天零采用**——已安装的插件没有任何一个会写这个字段；只有这一条
规则的话，几乎所有调用都会落 unknown，系统等于空转。

**Why this was ruled out (if not chosen):** 不能作为唯一来源。留作**最高优先级**
的那一级。

---

### Option 3: 只做名名前缀启发式

**Description:** 用工具名的下划线前缀匹配 bundle 行 id 与模块名，认不出就 unknown。

**Pros:** 零协调——不用任何插件作者配合，当场可用；证据支持前缀确实是生态里
既有的事实约定（`@hyzyn/dsh-kit` 的 tier-gate 就按 tool 名前缀分流；
ADR-0001 刚用同类约定解决过侧栏条目的身份问题）。

**Cons:** 依赖命名约定而非官方契约，可能误判；工具名首段与包名片段偶然相同的
时候会错配；带下划号的核心工具（`todo_write` 等）会落 unknown。

**Why this was ruled out (if not chosen):** 不能作为唯一来源——它有明确的误判面，
而自报声明没有。

---

### Option 4: 自报声明优先 + 前缀启发式兜底（两层）

**Description:** 解析顺序固定为：① 自报声明精确命中 → `high`；② MCP 形状的
工具名 → `mcp:<服务器名>`；③ 技能 → `skill:<技能名>`；④ 前缀启发式：归一化后与
行 id / 模块名**完全相等** → `high`，落在模块名**一段**里且唯一命中 → `medium`，
命中多个插件 → `low`；⑤ 都不中 → `unknown`。

**Pros:** 自报声明一旦被采用就立刻升级到精确；启发式让系统今天就能工作；
置信度把「确定」与「推断」分开，统计层可以只信 `high`/`medium`；`unknown`
如实保留，不污染任何插件的用量。

**Cons:** 启发式仍有误判面；两套规则要各自维护；匹配逻辑（归一化、噪声词、
连续段匹配、按模块去重）比「等值查表」复杂。

**Why this was ruled out (if not chosen):** —— 即所选方案。

---

### Option 5: 把 FR-1 / FR-2 并入 `dsh-toomuch-plugins`

**Description:** 在本插件的 Host 半边里加采集器与归属层。

**Pros:** 不发第二个 npm 包；发布流程不动；复用现有的 Typert 服务与 JSON 存储
约定。

**Cons:** 每个只想「收起侧栏」的用户都会被装上遥测采集器；把两个无关产品
绑进一个发布节奏；违背 `docs/design.md` §2 已声明的边界与 §10「更适合别的插件
去做」的既有判断。

**Why this was ruled out (if not chosen):** 归属层是**跨插件**的基础设施，不是
侧栏功能的一部分。

---

### Option 6: 另开一个独立仓库

**Description:** 新建 `dsh-plugin-insight` 独立仓库。

**Pros:** 仓库边界最干净；发布、版本、市场条目完全独立。

**Cons:** 本次会话的文件写权限只覆盖本工作区，另开仓库需要额外授权；两个仓库
之间的文档（术语表、ADR）需要复制或同步。

**Why this was ruled out (if not chosen):** 见下面的落点决策。

---

### Option 7: 本仓库内独立子包 `packages/dsh-plugin-insight/`

**Description:** 同一个仓库里放两个 npm 包：主包 `dsh-toomuch-plugins` 与子包
`dsh-plugin-insight`。子包有自己的 `package.json`、`cordis.patch.yml`、`src/`，
安装后是一条**独立的** bundle 记录。

**Pros:** 物理上在本工作区内、可完整落地与测试；运行时**零耦合**——用户装
主包不会带上采集器；子包将来可单独发 npm，也可先只用 `link:` 装；
文档与术语表仍在一处。

**Cons:** 仓库同时管两个包，发布流程将来要加一节；子包与主包的版本号各自独立。

**Why this was ruled out (if not chosen):** —— 即所选方案。

---

## Decision

**我们采用 Option 4 的两级归属来源**（自报声明优先、前缀启发式兜底、认不出就标
unknown），**并把 FR-1 / FR-2 放在 Option 7 的独立子包 `packages/dsh-plugin-insight/`**，
不并入 `dsh-toomuch-plugins` 的运行时。

具体四件事：

1. **归属值域固定**为 `pkg:<模块说明符>` / `builtin` / `mcp:<服务器名>` /
   `skill:<技能名>` / `unknown`，置信度为 `high` / `medium` / `low` / `unknown`。
2. **两级来源**：插件自报（`package.json` 的 `dsh.capabilities`）→ `high`；
   前缀启发式 → 完全相等 `high`、连续段唯一命中 `medium`、多候选 `low`；
   都不中 → `unknown`。
3. **事件订阅按真实存在的 cordis 事件写**：`tools/pre-execute` + `tools/result`
   （工具调用与耗时）、`session/event`（`command/run`、`approval/asked`、
   `approval/decided`）、`agent/pre-step`（用户 `/技能名` 手势）、
   `plugin-manager/changed`（编排变化）。**不使用** `skill/invoke`、
   `agent/session-start`、`command/run` 作为 cordis 事件——前两者不存在，
   第三者只是会话日志事件类型。
4. **落盘只写最小字段**（时间、类别、名字、会话、归属、耗时、是否出错），
   不写参数正文与结果正文；事件流在 `<DSH_HOME>/plugins/dsh-plugin-insight/events.jsonl`。

## Consequences

### Positive Consequences

- 归属层今天就能工作，且给未来的官方映射留好了替换位：官方契约一旦出现，
  只需替换前缀启发式那一级，自报声明与置信度模型都不用动。
- 「确定」与「推断」分开：统计层只信 `high` / `medium`，`low` 与 `unknown`
  单独看，不会把猜出来的归属算进某个插件的用量。
- 自报声明同时是一份**能力档案**：FR-3 的能力矩阵可以直接从它长出来。
- 侧栏插件的运行时保持干净：装侧栏插件的用户不会被装上采集器。
- 术语表（根目录 `GLOSSARY.md`）把「插件 / bundle 行 / 归属 / 置信度」钉死，
  两条产品线共用一套词。

### Negative Consequences / Accepted Tradeoffs

- **前缀启发式会误判。** 工具名首段恰好与某个无关插件的包名片段相同时会错配。
  接受它，代价是置信度 `medium` / `low` 会真实存在——这是明码标价，不是隐藏。
- **带下划号的核心工具认不出归属**（`todo_write`、`create_goal` 等）会落
  `unknown`。宿主自带工具一律无前缀（`bash` / `read` / `edit` / `write` /
  `grep` / `glob`），这条规则覆盖了绝大多数；剩下的少数先认作 unknown。
- **用户批准记成独立事件行**，不与工具调用合并——合并要处理时序竞争
  （审批事件是持久流的异步投递，可能晚于 `tools/result`），收益不抵复杂度。
  统计层按 `callId` 自行关联。
- **仓库要管两个 npm 包。** 主包的发布流程完全不变（主包 `files` 白名单不含
  `packages/`），子包先用 `link:` 装，等独立成熟了再单独发 npm。

### Risks

- **上游改了工具命名**：插件改工具名 → 归属跟着改，这是启发式的固有代价。表现是
  某个插件的用量突然归零或落到 unknown，不会报错。
- **上游改了事件协议**：`tools/*` 与 `session/event` 是 dsh-tools / dsh-session 的
  内部契约，改名会让采集层收不到事件。表现是事件流变空，不崩。
- **子包长期不发 npm**：只有本机 `link:` 装，别的用户用不上——这是有意的节奏，
  不是缺陷。

## Implementation Notes

- 代码：`packages/dsh-plugin-insight/`
  - `src/attribution.js`——归属解析层（FR-2）。纯函数与解析器同文件，便于单测。
  - `src/collect.js`——采集层（FR-1）。事件订阅与事件行组装。
  - `src/store.js`——JSONL 追加写。写失败只丢这一行，不打断运行时。
  - `src/index.js`——装配两层并 `ctx.provide('pluginInsight', …)`。
- 关键实现点：
  - **前缀候选从长到短**：`skill_manager_list` 要先试 `skill_manager`（命中
    `skill-manager`），再试 `skill`（会命中一串插件）。从长到短是让精确匹配
    抢先的唯一办法。
  - **噪声词**：`dsh` / `plugin` / `ui` / `client` / `suite` / `runtime` 等在
    包名里不携带身份，比较前去掉，否则 `dsh-mattpocock-skills-deck` 永远配不上
    `deck`。
  - **按模块去重**：一个包可以插多行（`dsh-mattpocock-skills-deck` 插了两行，
    `@ericwang1358/dsh-daily-flashcard` 插了七行）。命中的是**行**，归属的
    是**模块**，所以要按模块去重，否则会误判成「多候选」。
  - **技能有两个来源**：用户手势走 `agent/pre-step` 的消息（不产生工具调用），
    模型调用走名为 `skill` 的工具（`arguments.name` 是技能名）。两者都记成
    `kind='skill'`，用 `source` 区分。
- 验证：`node packages/dsh-plugin-insight/test/smoke.js`（归属解析 + 手势识别 +
  落盘往返）；本仓库既有门禁 `node test/smoke.js` 不受影响。

## Review Date

触发下列任一情况即复审：

- DSH 公开了「工具名 → 插件」的官方映射（届时应加 `adapter-official` 一级，
  替换前缀启发式）；
- 已安装插件开始成规模采用 `dsh.capabilities` 自报声明（届时启发式可以降级为
  纯兜底，甚至只保留声明级）；
- DSH 改了 `tools/*` 或 `session/event` 的事件名与载荷。
